# 三重验证感知链:OCR + 本地语义解析 + 大模型图片推理的速度妥协方案

> **文档性质**:架构设计笔记(基于真实实测数据)
> **日期**:2026-08-11
> **相关**:docs/competitor-nuphus-mcp.md(竞品参考)

## 一、背景与问题

全局 AI 助手需要"看懂屏幕"才能执行操作。当前候选的感知手段有三层:

1. **OCR(本地)**:识别屏幕文字及坐标(rapidocr / PaddleOCR)
2. **本地语义解析**:窗口枚举、UIA 控件树、YOLO 图标检测(零网络,毫秒级)
3. **大模型图片推理**:mimo-v2.5 视觉模型,理解语义(1-3s,有歧义风险)

**核心矛盾**:越"聪明"的层越慢;而桌面助手对简单操作的响应要求是 **<2s 快速反馈**。

## 二、实测数据(本机 RTX 4060 Laptop, 2560×1440)

### OCR(rapidocr-onnxruntime, PP-OCRv4)

| 配置 | 耗时 | 说明 |
|---|---|---|
| CPU 全图 | **9323ms** | ❌ 不可用 |
| CPU + 关cls + side1280 | 6579ms | ❌ 不可用 |
| DML(GPU)全图首轮 | 3852ms | 含模型初始化 |
| **DML 全图热推理** | **1218ms** | ✅ 可用 |
| **DML + side1280 限制** | **1030ms** | ✅ 可用 |
| **DML + 中央区域裁剪** | **536ms** | ✅ 快 |

**结论:GPU(DML)是 OCR 提速的第一杠杆(7-9x),区域裁剪是第二杠杆(再 2x)。组合后 OCR 从 9.3s → 0.5s。**

### 其他链路(既有实测)

| 环节 | 耗时 | 说明 |
|---|---|---|
| 截图(ImageGrab 合成画面) | 231-255ms | 大开销,二期可换 DXGI(~10ms) |
| 窗口枚举(热路径) | 45ms | 进程名缓存后 |
| 前台窗口获取 | <1ms | 瞬时 |
| 后台点击(PostMessage) | 15μs | 几乎为零 |
| 最小化/恢复窗口 | 26-398ms | 首次含动画 |

## 三、三层感知的正确分工(速度妥协核心)

**原则:能用便宜的绝不用贵的;贵的只做它擅长的事(语义),不做它不擅长的事(坐标)。**

```
用户指令
    │
    ├─ ① 窗口/进程级(纯本地,<50ms)★ 最常用
    │    枚举窗口 → 标题匹配 → "打开微信""最小化这个" 直接命中
    │    不需要任何视觉!窗口操作 95% 走这层
    │
    ├─ ② 本地语义解析(UIA + OCR,<1.2s)
    │    UIA 控件树读按钮/输入框(精确坐标,零歧义)
    │    OCR 补位:自绘界面/游戏 UIA 读不到 → GPU OCR 找文字
    │    YOLO 图标检测:无文字的图标按钮(可选增强)
    │    输出:元素列表[{id, text, rect, kind}] — 纯文本,毫秒级
    │
    └─ ③ 大模型图片推理(1-3s)★ 最后手段
         视觉模型理解复杂界面/模糊指令
         ★ 关键设计:视觉模型只输出"选哪个元素"(语义决策)
           → 坐标由 ② 层提供(OCR/UIA 精确框)
           → 绝不直接信任视觉模型猜的坐标(实测翻车:认错"+"按钮)
```

### 双速推理映射

| 指令复杂度 | 走哪层 | 目标延迟 |
|---|---|---|
| 窗口操作("打开微信") | ① 本地窗口级 | **<100ms** |
| 有明确文字("点发送") | ② UIA/OCR | **<1.5s** |
| 模糊/复杂("这个界面怎么退出登录") | ③ 视觉 LLM | 2-3s |

**简单操作绝不深度思考** — 这正是用户要求的产品核心体验。

## 四、工程优化清单(按收益排序)

### P0:GPU 加速(已实测 +17x)
- 装 `onnxruntime-directml`(保留 DML EP,卸载 CPU 版 onnxruntime 防冲突)
- rapidocr 配置 `Det/Rec/Cls.use_dml: true`,关 cls(方向分类,收益小)
- 陷阱:rapidocr 依赖会拉回 CPU 版 onnxruntime → 需 `pip uninstall onnxruntime` 保留 directml

### P1:区域化感知(已实测再 +2x)
- 永远不要全屏 OCR!先用窗口枚举定位目标窗口 → 只对该窗口区域 OCR
- `max_side_len` 限制到 1280(检测输入尺寸)

### P2:模型常驻(借鉴 nuphus 的 OnceLock 共享引擎)
- OCR/YOLO 引擎进程级单例,避免每次调用重载模型(80MB)
- nuphus 明确标注这是 P1 优化:每次调用重新提交模型 = 慢到不可用

### P3:UIA 优先于 OCR
- UIA 控件树毫秒级且零歧义,应作为"找按钮"的第一手段
- OCR 只做 UIA 读不到的补位(自绘界面、游戏、图像内容)

### P4:大模型只做语义选择
- 视觉 LLM 收到的是元素列表(文字版)而非裸截图 → 更便宜更快
- 必要看截图时,让模型输出"选择元素 id"而不是"给出坐标"

## 五、可借鉴的开源组件(与 nuphus-mcp 对比)

| 组件 | 用途 | 借鉴点 |
|---|---|---|
| **rapidocr-onnxruntime**(Apache-2.0) | OCR | ✅ 已选,ONNX 轻量,DML 加速 |
| **nuphus-mcp perceive 合并引擎**(MIT) | OCR+YOLO 融合 | IoU 合并、共享引擎(OnceLock)、类型推断启发式(宽高比>3=输入框) |
| **OmniParser icon_detect**(微软) | 图标检测 YOLO | 80MB onnx,nuphus 直接用的这个模型 |
| **PaddleOCR 模型**(Apache-2.0) | 检测+识别 | PP-OCRv4,轻量(det 4.6MB + rec 10.6MB) |
| **UIAutomation**(Windows 内置) | 控件树 | 零模型成本,毫秒级,第一优先 |

### nuphus 的启发式类型推断(可直接抄)
```
宽高比 > 3 → Input(输入框)
含关键词(输入/搜索/密码/username)→ Input
1-4 字符无标点 → Button
默认 → Text
```

## 六、结论

**三重验证不是"三个都跑取多数",而是"阶梯降级 + 各司其职":**

1. **窗口级(本地,<50ms)** → 处理 95% 窗口操作,零视觉成本
2. **UIA/OCR(本地,<1.2s)** → 精确坐标,GPU 加速后实时可用
3. **视觉 LLM(1-3s)** → 只做语义决策,坐标回填本地层

配合 GPU 加速(17x)和区域化(2x),**OCR 从 9.3s 降到 0.5s**,简单操作全程 <1.5s,满足"快速反馈"产品要求。
